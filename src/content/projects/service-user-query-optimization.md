서비스 담당자 조회 API에서 유저마다 상세정보와 등록자를 조회하던 흐름을 일괄 조회로 바꾸고, 응답 데이터는 사번을 키로 한 `HashMap`에서 조합했다.

## 문제와 원인

DB 계정 작업 요청 티켓에서 패스워드 확인 버튼이 늦게 노출된다는 제보를 계기로 서비스 담당자 조회 API의 지연을 확인했다. 당시 운영 데이터 68명을 조회했을 때 응답에 3초 이상 걸리고 SQL이 약 200회 실행되는 것을 확인했다.

기존 코드는 서비스 유저 목록을 조회한 다음 Java `for` 문에서 각 유저의 상세정보(이름·부서)와 등록자 정보를 jOOQ Repository Query로 조회했다. 이는 ORM의 지연 로딩이 아니라 **애플리케이션 코드가 반복문 안에서 조회 Query를 호출해 발생한 N+1 형태의 문제**다.

```text
서비스 유저 목록 조회
  → 유저별 상세정보 조회
  → 유저별 등록자 정보 조회
  → 다음 유저에서 두 조회 반복
```

위 흐름의 조회만 계산하면 68명에 대해 **137회(1 + 68 × 2)**다. 실제 확인한 약 200회와 차이가 있지만 **SQL 집계 범위와 차이의 원인은 확인되지 않았다.**

## 일괄 조회와 데이터 조합

서비스 유저 목록, 유저 상세정보, 등록자 상세정보를 각각 한 번씩 조회하도록 바꿨다. 조회한 상세정보와 등록자 정보는 사번을 키로 하는 `HashMap`에 담고, 서비스 유저를 순회하면서 Map에서 찾아 응답을 구성했다.

```text
기존: 서비스 유저 목록 조회 → 유저별 상세정보·등록자 정보 반복 조회

개선: 서비스 유저 목록 조회 (1회)
      + 유저 상세정보 일괄 조회 (1회)
      + 등록자 상세정보 일괄 조회 (1회)
      → 사번 기준 HashMap 조합 → 응답
```

개선한 조회 흐름에서는 유저별 반복문 안에서 추가 SQL을 실행하지 않는다. 따라서 이 흐름의 조회 횟수는 유저 수에 비례해 늘어나지 않는다.

## JOIN 1회 조회 대신 일괄 조회를 선택한 이유

JOIN으로 필요한 데이터를 한 Query에서 가져오는 방안도 검토했다. 기존 Repository Query를 일괄 호출하는 방식으로 **유저 수에 비례하는 반복 조회**를 없앨 수 있어 API 전용 JOIN Query를 추가하지 않았다. 이 선택에는 세 번의 DB 조회와 Java에서의 Map 조합이 따른다.

## 결과

| 운영 데이터 68명 조회 | 기존 | 개선 후 |
| --- | --- | --- |
| SQL 실행 횟수 | 약 200회 | 3회 |
| API 응답 시간 | 3초 이상 | 1초 미만 |

위 수치는 운영 환경에서 68명을 조회했을 때 확인한 전후 값이다. 다른 조회 규모에서의 응답 시간이나 각 변경 요소의 개별 기여도까지 나타내지는 않는다.
