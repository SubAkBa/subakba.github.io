## 문제와 원인

- DB 계정 작업 요청 티켓의 패스워드 확인 버튼이 늦게 노출된다는 사용자 제보에서 서비스 담당자 조회 API의 지연 확인
- 운영 데이터 **68명** 조회에 **3초 이상** 소요, SQL **약 200회** 실행
- 서비스 유저 목록을 조회한 뒤 Java `for` 문에서 각 유저의 상세정보와 등록자 정보를 jOOQ Repository Query로 반복 조회
- 사용자 수에 비례해 쿼리가 늘어나는 N+1 형태의 구조가 DB 접근과 네트워크 왕복 비용을 증가시킴

```text
서비스 유저 목록 조회
        ↓
서비스 유저 68명 순회
        ├── 유저 상세정보 조회 (이름·부서)
        └── 등록자 상세정보 조회
        ↓
운영 환경에서 약 200회 SQL 실행
```

> ORM의 지연 로딩이나 엔티티 연관관계가 아닌, Java 반복문 안에서 조회 쿼리를 직접 호출해 발생한 문제.

## 개선 방법 검토

| 방식 | 장점 | 검토 결과 |
| --- | --- | --- |
| JOIN 기반 전용 Query | 필요한 데이터를 한 번에 조회 가능 | API 응답 형태에 특화된 Query 추가가 필요하고, 재사용 가능성이 낮으며 조회 책임과 Query 복잡도가 증가 |
| 기존 Query 재사용 + 일괄 조회 | 기존 Repository Query를 활용하면서 반복 호출 제거 | 3회 조회로 DB 접근 횟수를 충분히 줄이고, 전용 Query 추가 없이 데이터 조합 가능 |

- 핵심 목표를 쿼리 1회 실행이 아니라 **사용자 수에 비례하는 반복 조회 제거**로 설정
- 기존 Query의 재사용성과 단순한 구조를 유지할 수 있는 일괄 조회 방식 선택

## 일괄 조회와 데이터 조합

- 서비스 유저 목록, 유저 상세정보, 등록자 상세정보를 각각 한 번씩 조회하도록 변경
- 상세정보와 등록자 정보를 사번을 Key로 하는 `HashMap`에 적재
- 서비스 유저를 순회할 때 DB를 다시 조회하지 않고 Map에서 필요한 데이터를 찾아 응답 구성

```text
Before: 목록 조회 → 유저별 상세정보·등록자 정보 반복 조회 → 약 200회 Query

After:  서비스 유저 전체 조회
        + 유저 상세정보 전체 조회
        + 등록자 상세정보 전체 조회
        → 3회 Query → 사번 기준 HashMap 데이터 조합
```

서비스 유저 수가 늘어나도 이 API의 조회 Query 실행 횟수는 최대 3회로 유지되는 구조.

## JOIN 1회 조회 대신 일괄 조회를 선택한 이유

- 전용 JOIN Query는 이 API의 응답 구조에만 맞춰져 다른 기능에서 재사용하기 어려움
- 여러 조회 책임을 한 Query에 결합하면 응답 데이터 변경 시 Query 수정 범위와 복잡도 증가
- 기존 Repository Query를 3회 일괄 실행하는 방식으로도 사용자 수에 비례하는 반복 조회를 제거할 수 있다고 판단

## 결과

- **Query 실행 횟수: 약 200회 → 3회** (운영 데이터 68명 조회 기준)
- **API 응답 시간: 3초 이상 → 1초 미만** (운영 환경 기준)
- Java 반복문 내부의 조회 호출을 제거하여 사용자 수에 따라 Query가 증가하던 구조 개선
- 기존 Repository Query를 재사용해 API 전용 JOIN Query 추가 없이 패스워드 확인 기능의 체감 지연 개선
